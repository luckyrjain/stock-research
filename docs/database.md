# Database Schema Reference

PostgreSQL schema for AlphaPulse. **21 tables**, all declared against one shared SQLAlchemy Core
`MetaData()` in `backend/db/models.py` — that file is the single source of truth for schema.

| Artifact | Status |
|---|---|
| `backend/db/models.py` | **Authoritative.** 21 `Table(...)` definitions + `get_engine()` + `stamp_alembic_head()`. |
| `backend/migrations/versions/*.py` | **Authoritative for applying schema.** 3 revisions, chained. Autogenerated from `db.models.metadata`. |
| `backend/db/schema.sql` | **NOT authoritative.** Frozen pre-Alembic reference, covering only the original 11 tables. Kept as history and because `tests/test_schema_sql_migrations.py` still exercises its `IF NOT EXISTS` guard convention for 2 tables. It is not expected to gain new `ALTER TABLE` guards; new columns get an Alembic revision instead. |

`DATABASE_URL` (a PostgreSQL DSN) is the only connection config. It is read directly by
`db.models.get_engine()`, `migrations/env.py`, and every module's own lazy `_get_engine()` — there
is no central config module. See [DATABASE_URL is optional](#database_url-is-optional) for what
runs without it.

## Conventions

- **Timestamps** are `TIMESTAMPTZ`. Most default to `NOW()`; the six Portfolio Aggregator tables use
  `CURRENT_TIMESTAMP` instead because their tests run `metadata.create_all()` against SQLite, where
  `NOW()` does not exist. Every other table is only ever tested through a mocked engine, so
  portability never came up.
- **Money/ratios** are `NUMERIC` with explicit precision, never float. Read paths cast at the query
  boundary (`current_price::float AS current_price`).
- **JSON columns** (`assets.meta`, `transactions.meta`) use SQLAlchemy's generic `JSON`, not
  Postgres `JSONB` — same SQLite-test-backend reason. No JSONB-only operator (containment, path
  queries) is used anywhere, so nothing is lost.
- **Writes are idempotent upserts** keyed on the table's natural unique constraint
  (`ON CONFLICT ... DO UPDATE`), so re-running a pipeline or re-analysing a symbol the same day
  never duplicates rows.
- **Never invent.** A column is `NULL` when the source did not supply it — never 0, never a guess.
  This is why so many columns are nullable.

## Accounts / auth

Backing module: `backend/auth.py` (all reads and writes). Endpoints live in `backend/api.py`
(`/api/auth/*`, `/api/api-keys*`).

`auth.py` deviates from this codebase's usual swallow-and-log convention: `create_magic_link`,
`verify_magic_link`, and `create_session` **raise** on a DB failure, because a broken auth write
must surface as an error rather than silently pretend a link was sent. Read paths
(`get_user_for_session`, `get_user_for_api_key`) degrade to "not signed in" instead, so a DB hiccup
does not 500 every authenticated page load.

### `users`

| Column | Type | Null | Default |
|---|---|---|---|
| `id` | `INTEGER` | no | identity (PK) |
| `email` | `VARCHAR(320)` | no | — |
| `created_at` | `TIMESTAMPTZ` | yes | `NOW()` |
| `tier` | `VARCHAR(10)` | no | `'free'` |

- PK `id`; `UNIQUE (email)`; `CHECK tier IN ('free','pro')` (`ck_users_tier`).
- Referenced by `sessions.user_id`, `api_keys.user_id`, `watchlist_items.user_id`,
  `positions.user_id` — all plain FKs, **no `ON DELETE` action** (see
  [Known schema gaps](#known-schema-gaps)).
- **Writes:** `auth.verify_magic_link()` only — `INSERT ... ON CONFLICT (email) DO UPDATE`, so the
  first successful magic-link click *is* account creation.
- **Reads:** `auth.get_user_for_session()`, `auth.get_user_for_api_key()`,
  `watchlist_alerts._get_watched_symbols()` (joins to get the alert email).
- **Lifecycle:** grows only. No delete path exists anywhere in the codebase. `tier` is set by an
  operator by hand — there is no checkout flow that ever writes `'pro'`.

### `magic_links`

| Column | Type | Null | Default |
|---|---|---|---|
| `id` | `INTEGER` | no | identity (PK) |
| `email` | `VARCHAR(320)` | no | — |
| `token_hash` | `VARCHAR(64)` | no | — |
| `expires_at` | `TIMESTAMPTZ` | no | — |
| `used_at` | `TIMESTAMPTZ` | yes | — |
| `created_at` | `TIMESTAMPTZ` | yes | `NOW()` |

- PK `id`; `UNIQUE (token_hash)`; index `idx_magic_links_email (email)`.
- **Writes:** `auth.create_magic_link()` (insert), `auth.verify_magic_link()` (consume).
- **Reads:** consumption is the read — `UPDATE ... WHERE token_hash = :h AND used_at IS NULL AND
  expires_at > NOW() ... RETURNING email`, so two concurrent clicks of the same link cannot both win.
- **Lifecycle:** TTL 15 minutes (`auth.MAGIC_LINK_TTL`). Pruned opportunistically — every
  `create_magic_link()` call first runs `DELETE FROM magic_links WHERE expires_at < NOW()`. No cron.

### `sessions`

| Column | Type | Null | Default |
|---|---|---|---|
| `id` | `INTEGER` | no | identity (PK) |
| `user_id` | `INTEGER` | no | → `users.id` |
| `token_hash` | `VARCHAR(64)` | no | — |
| `expires_at` | `TIMESTAMPTZ` | no | — |
| `created_at` | `TIMESTAMPTZ` | yes | `NOW()` |

- PK `id`; FK `user_id → users.id`; `UNIQUE (token_hash)`; index `idx_sessions_user (user_id)`.
- **Writes:** `auth.create_session()` (insert), `auth.delete_session()` (logout,
  `DELETE ... WHERE token_hash = :h`, best-effort).
- **Reads:** `auth.get_user_for_session()` on every authenticated request, keyed by `token_hash`.
- **Lifecycle:** TTL 30 days (`auth.SESSION_TTL`). Pruned in the same
  `create_magic_link()` transaction as `magic_links` (`DELETE FROM sessions WHERE expires_at < NOW()`)
  — so a deployment where nobody requests a new sign-in link never prunes expired sessions.
  Harmless (expiry is checked on read), but the table is not self-cleaning under idle traffic.

### `api_keys`

| Column | Type | Null | Default |
|---|---|---|---|
| `id` | `INTEGER` | no | identity (PK) |
| `user_id` | `INTEGER` | no | → `users.id` |
| `key_hash` | `VARCHAR(64)` | no | — |
| `key_prefix` | `VARCHAR(16)` | no | — |
| `label` | `VARCHAR(120)` | yes | — |
| `created_at` | `TIMESTAMPTZ` | yes | `NOW()` |
| `last_used_at` | `TIMESTAMPTZ` | yes | — |
| `revoked_at` | `TIMESTAMPTZ` | yes | — |

- PK `id`; FK `user_id → users.id`; `UNIQUE (key_hash)`; index `idx_api_keys_user (user_id)`.
- `key_prefix` is not secret (first few chars of the raw key) — it exists so the management UI can
  list keys distinguishably without ever re-displaying the secret.
- **Writes:** `auth.create_api_key()` (insert), `auth.revoke_api_key()` (sets `revoked_at`, never
  deletes the row), `auth.get_user_for_api_key()` (opportunistically stamps `last_used_at`).
- **Reads:** `auth.get_user_for_api_key()` on every `GET /api/v1/*` call, keyed by `key_hash`;
  `auth.list_api_keys()` for the management UI.
- **Lifecycle:** no TTL, unlike a session — a key is valid until revoked, since a script cannot
  redirect through a magic link. Revoked rows are retained (badged in the UI), so the table only grows.

## Cross-mode user data

Backing modules: `backend/routes/watchlist.py`, `backend/routes/positions.py`, and the shared
`backend/routes/_shared.py`. Both tables share the same ownership shape and the same helpers
(`resolve_owner()`, `owner_column()` — both live in `watchlist.py` and are imported by
`positions.py`; nothing about them is watchlist-specific).

### `watchlist_items`

| Column | Type | Null | Default |
|---|---|---|---|
| `id` | `INTEGER` | no | identity (PK) |
| `client_id` | `VARCHAR(36)` | yes | — |
| `user_id` | `INTEGER` | yes | → `users.id` |
| `symbol` | `VARCHAR(20)` | no | — |
| `company` | `VARCHAR(200)` | yes | — |
| `exchange` | `VARCHAR(5)` | yes | — |
| `added_at` | `TIMESTAMPTZ` | yes | `NOW()` |

- PK `id`; FK `user_id → users.id`.
- `CHECK ((client_id IS NULL) <> (user_id IS NULL))` — `ck_watchlist_exactly_one_owner`.
- `UNIQUE (client_id, symbol)` — `uq_watchlist_client_symbol`.
- `UNIQUE (user_id, symbol)` — `uq_watchlist_user_symbol`.
- Indexes `idx_watchlist_client (client_id)`, `idx_watchlist_user (user_id)`.
- **Writes:** `routes/watchlist.py` — `POST /api/watchlist` (upsert under a per-owner
  `pg_advisory_xact_lock`, capped at `_MAX_WATCHLIST_ITEMS_PER_CLIENT` = 200),
  `DELETE /api/watchlist/{symbol}`, `POST /api/watchlist/claim` (via
  `routes/_shared.py::claim_anonymous_rows_sync`).
- **Reads:** `GET /api/watchlist` (frontend `useWatchlist()`); `watchlist_alerts._get_watched_symbols()`
  joins to `users` with `WHERE user_id IS NOT NULL` — anonymous rows have no email and are excluded
  at the query level.
- **Lifecycle:** user-driven only. No pruning, no cron, no expiry. An anonymous browser that clears
  `localStorage` orphans its rows permanently (they stay under a `client_id` nobody will ever send
  again) — there is no reaper for them.
- `GET /api/watchlist/calendar` is deliberately **not** a query against this table: the frontend
  passes its own symbol list, and the endpoint classifies each symbol's already-cached `filings`.

### `positions`

| Column | Type | Null | Default |
|---|---|---|---|
| `id` | `INTEGER` | no | identity (PK) |
| `client_id` | `VARCHAR(36)` | yes | — |
| `user_id` | `INTEGER` | yes | → `users.id` |
| `symbol` | `VARCHAR(20)` | no | — |
| `company` | `VARCHAR(200)` | yes | — |
| `exchange` | `VARCHAR(5)` | yes | — |
| `entry_price` | `NUMERIC(14,4)` | yes | — |
| `target_price` | `NUMERIC(14,4)` | yes | — |
| `stop_loss` | `NUMERIC(14,4)` | yes | — |
| `shares` | `NUMERIC(16,4)` | yes | — |
| `bought_at` | `TIMESTAMPTZ` | yes | `NOW()` |

- PK `id`; FK `user_id → users.id`.
- `CHECK ((client_id IS NULL) <> (user_id IS NULL))` — `ck_positions_exactly_one_owner`.
- `UNIQUE (client_id, symbol)` — `uq_positions_client_symbol`.
- `UNIQUE (user_id, symbol)` — `uq_positions_user_symbol`.
- Indexes `idx_positions_client (client_id)`, `idx_positions_user (user_id)`.
- `shares` is user-entered, never scraped or derived. It stays `NULL` (not `0`, not an assumed `1`)
  until the user fills it in on `/portfolio`. The capital-weighted portfolio stats are computed only
  over positions that actually have it, and are labelled with how many of the total contribute.
- **Writes:** `routes/positions.py` — `POST /api/positions` (upsert; a re-mark refreshes
  entry/target/stop but deliberately leaves `shares` and `bought_at` untouched),
  `PATCH /api/positions/{symbol}` (`shares` only), `DELETE /api/positions/{symbol}`,
  `POST /api/positions/claim`. Same 200-row cap (`_MAX_POSITIONS_PER_CLIENT`) and advisory-lock
  pattern as the watchlist.
- **Reads:** `GET /api/positions`; `routes/positions.py::compute_sector_concentration()` for
  `GET /api/portfolio/concentration` (capital-weighted, excluding any position missing `shares`, a
  live price, or a cached sector).
- **Lifecycle:** identical to `watchlist_items` — user-driven, no pruning.

> `positions` is unrelated to the Portfolio Aggregator's `assets`/`holdings` tables below. It tracks
> Market Picks marks; the Aggregator tracks personal net worth. They share only the word "portfolio"
> and the `/api/portfolio/*` URL prefix.

### The dual-ownership model

Each row is owned by **exactly one** identity: an anonymous per-browser `client_id` (a
`crypto.randomUUID()` kept in `localStorage`) or a signed-in account's `user_id`. Never both, never
neither.

**Why two separate unique constraints and not one combined `UNIQUE (client_id, user_id, symbol)`:**
Postgres treats every `NULL` as distinct from every other `NULL` in a unique index. Under a combined
constraint, every account-owned row has `client_id IS NULL` and every anonymous row has
`user_id IS NULL`, so no two rows would ever be considered equal — the constraint would permit
unlimited duplicate `(user_id, symbol)` and `(client_id, symbol)` pairs, i.e. it would cap nothing.
Two constraints, each over a single owner column plus `symbol`, are what actually enforce
one-row-per-symbol-per-identity. The `CHECK` is what stops a row from dodging both by populating
neither column.

**Identity resolution** (`routes.watchlist.resolve_owner()`): a valid `Authorization: Bearer <token>`
session always wins over a supplied `client_id`, since the point of an account is not depending on
which browser sent the request. An expired or invalid token is **not** a 401 here — these endpoints
do not require sign-in, so it falls through to the `client_id` path. Neither a valid session nor a
well-formed `client_id` → 422.

**No automatic migration on sign-in.** Signing in never claims or merges an anonymous browser's rows
onto the account. A freshly-signed-in user simply sees whatever their account already owns.

**Opt-in claim flow** — `POST /api/watchlist/claim` and `POST /api/positions/claim`, both requiring a
valid session (a missing/expired one is a real 401 here, not a fall-through). Both call the one
shared `routes/_shared.py::claim_anonymous_rows_sync(engine, table, order_column, client_id, user_id,
max_per_owner, lock_prefix)`:

1. Takes `pg_advisory_xact_lock` on the **same** per-account key the add endpoint uses
   (`{prefix}:user:{user_id}`), then a second lock on `{prefix}:client:{client_id}`, always in that
   order so two callers can never deadlock. Using a distinct "claim" lock namespace was an earlier
   bug — a concurrent claim and add took different locks, never serialized, both read the same
   pre-write count, and together exceeded the cap.
2. Deletes anonymous duplicates of symbols the account already owns (they could never be claimed —
   `uq_{table}_user_symbol` forbids it).
3. Reassigns rows oldest-first (`ORDER BY {added_at|bought_at} ASC`) up to the account's remaining
   room under the 200-row cap. Overflow is left owned by `client_id` and reported as `skipped`,
   never silently dropped.

**Disclosed residual risk:** `client_id` was never a secret — it appears in plaintext query strings
on the ordinary read/write endpoints, so it can leak via a screenshot, browser history, or an access
log. Claiming is more severe than an ordinary write because it *exclusively* reassigns rows, cutting
off the original browser. Both claim endpoints are rate-limited to 5/hour (vs. 60/minute for
ordinary writes) and log a `watchlist_claimed`/`positions_claimed` audit event, which bounds
automated abuse but does not stop a single targeted guess of one leaked ID. A real fix needs proof
of possession (a signed token minted into the anonymous browser), not attempted.

## History / snapshots

### `verdict_history`

| Column | Type | Null | Default |
|---|---|---|---|
| `id` | `INTEGER` | no | identity (PK) |
| `symbol` | `VARCHAR(20)` | no | — |
| `verdict_date` | `DATE` | no | — |
| `recommendation` | `VARCHAR(10)` | yes | — |
| `confidence` | `VARCHAR(10)` | yes | — |
| `current_price` | `NUMERIC(14,4)` | yes | — |
| `signal_score` | `NUMERIC(6,2)` | yes | — |
| `created_at` | `TIMESTAMPTZ` | yes | `NOW()` |

- PK `id`; `UNIQUE (symbol, verdict_date)` — `uq_verdict_history_symbol_date`;
  index `idx_verdict_history_symbol (symbol)`.
- No FK on `symbol` — symbols are not a table in this app's own domain (`securities` is an
  ingestion-side equity master, deliberately not a referential authority for user-facing symbols).
- **Writes:** `backend/verdict_history.py::save_snapshot(symbol, analysis, signal_context, stock_info)`
  — `ON CONFLICT (symbol, verdict_date) DO UPDATE`. Called from all three report-producing paths:
  `main.py`'s CLI (both the cache-hit early return and the full run), `api.py`'s
  `/api/analyse/{symbol}` SSE stream right after `_build_report()`, and
  `watchlist_alerts._analyze_symbol()` (including its own cache-hit path, so a day is never missing
  a snapshot just because nobody re-triggered the LLM).
- **Reads:** `verdict_history.load_history(symbol, limit=60)` (oldest-first) →
  `GET /api/verdict-history/{symbol}`, which additionally scores each stored verdict against today's
  live price; `watchlist_alerts._detect_change()` / `_detect_price_move()` compare the two most
  recent rows.
- **Lifecycle:** one row per (symbol, day) the pipeline actually ran. No pruning — grows with
  analysis traffic. `load_history`'s `limit` bounds the read, not the table.
- **Disclosed limitation:** plain last-write-wins. Two concurrent same-day analyses of the same
  symbol (a visitor and `watchlist_alerts.py --force`) can produce different LLM outputs; whichever
  commits last silently overwrites the other, and the change-detection diff may then compare against
  a row it did not write. Documented in the module docstring, not fixed.

### `mf_holdings_history`

| Column | Type | Null | Default |
|---|---|---|---|
| `id` | `INTEGER` | no | identity (PK) |
| `symbol` | `VARCHAR(20)` | no | — |
| `as_of_date` | `DATE` | no | — |
| `fund` | `VARCHAR(200)` | no | — |
| `holding_pct` | `NUMERIC(6,3)` | no | — |
| `created_at` | `TIMESTAMPTZ` | yes | `NOW()` |

- PK `id`; `UNIQUE (symbol, as_of_date, fund)` — `uq_mf_holdings_history_symbol_date_fund`;
  index `idx_mf_holdings_history_symbol (symbol)`.
- **Writes:** `backend/mf_holdings_history.py::save_snapshot(symbol, mf_holdings)`, called from
  `main._fetch_task()` — the one choke point both the CLI and the SSE endpoint funnel every data
  slice through — guarded to the `mf_holdings` task only, on both its raw-dict and parsed-JSON-text
  success paths. No-ops if `DATABASE_URL` is unset, the fetch was an error payload, `as_of_date` is
  missing, or there are no funds.
- **Reads:** `mf_holdings_history.compute_stake_deltas(symbol)` — ranks the most recent snapshot's
  funds and diffs each against the same fund in the second-most-recent snapshot. `delta_pct` is
  `NULL` when there is no prior snapshot or the fund is a new entrant.
- **Lifecycle:** cadence follows the `mf_holdings` cache TTL (168 h / 7 days) — `_fetch_task()` only
  runs for a task the freshness check marked stale, so a cache hit never reaches this. No separate
  poller, no pruning.
- `compute_stake_deltas()` is deliberately called by `api.py` via an *awaited* `run_in_executor` and
  passed *into* `main._build_report()` as a parameter, rather than called from inside it — it is a DB
  query, and `_build_report()` runs directly on the event loop.
- **Undisclosed-until-now matching risk:** the frontend matches a stored fund to a live-scraped fund
  by exact string on `fund`. A fund renaming itself, or Screener reformatting the same name between
  quarters, silently shows no delta badge rather than a wrong one.

## SME signals

Backing module: `backend/sme_ema_pipeline.py` (sole writer). Read by `api.py`'s
`GET /api/sme-signals`, `GET /api/sme-signals/{symbol}/history`, and the SME section of
`GET /api/consolidated/{symbol}`.

### `sme_stocks`

| Column | Type | Null | Default |
|---|---|---|---|
| `symbol` | `VARCHAR(20)` | no | PK |
| `name` | `TEXT` | yes | — |
| `exchange` | `VARCHAR(5)` | no | — |
| `isin` | `VARCHAR(12)` | yes | — |
| `series` | `VARCHAR(10)` | yes | — |
| `fetched_at` | `TIMESTAMPTZ` | yes | `NOW()` |
| `avg_volume_20d` | `NUMERIC(16,2)` | yes | — |
| `avg_turnover_20d` | `NUMERIC(16,2)` | yes | — |
| `market_cap_cr` | `NUMERIC(16,2)` | yes | — |

- PK `symbol`. No secondary indexes. Referenced by `ema_signals.symbol`.
- `exchange` is `'NSE'` (Emerge) or `'BSE'` (SME). For a BSE row, `symbol` is BSE's numeric scrip
  code, not a tradeable ticker — `isin` is what the frontend deep-links through
  `GET /api/validate/{isin}`. `isin` is always `NULL` for NSE rows (the NSE fetch never populates it).
- **Writes:** `_upsert_stocks()` (stock-list metadata, before OHLCV is fetched), then
  `_upsert_liquidity()` and `_upsert_market_cap()` as plain `UPDATE`s after the signal phase, since
  neither is known until then.
- **Lifecycle:** refreshed on every pipeline run. Liquidity/market-cap columns are `NULL` for any
  stock the run could not price — never backfilled with a guess. No deletes: a stock that leaves the
  SME list keeps its row with a stale `fetched_at`.

- **Writes:** `_upsert_signals()` — `INSERT ... ON CONFLICT ON CONSTRAINT uq_ema_signals_symbol_date
  DO UPDATE`. Only the last `_STORE_DAYS` (63, ~3 months of trading days) rows of a full year's
  computation are ever persisted; EMAs are computed over the full year first so the stored window's
  values are correct.
- **Reads:** `GET /api/sme-signals` (crosses view filters `cross_type IS NOT NULL`; `?view=regime`
  drops that filter and uses `DISTINCT ON (s.symbol) ... ORDER BY s.symbol, e.trade_date DESC`);
  the aggregate 90-day golden-cross hit rate via a
  `LEAD(close_price, 20) OVER (PARTITION BY symbol ORDER BY trade_date)` window function;
  `GET /api/sme-signals/{symbol}/history` for the chart and per-cross forward returns.
- **Retention:** `_prune_signals()` runs at the end of every pipeline run —
  `DELETE FROM ema_signals WHERE trade_date < CURRENT_DATE - INTERVAL ':days days'`, `_RETENTION_DAYS`
  = 100 calendar days (≈ 63 trading days + buffer). Forward-return history is bounded by this window;
  "last 3 golden crosses" can legitimately return fewer than 3, or zero.
- **Cron:** `.github/workflows/sme-cron.yml`, `0 13 * * 1-5` (13:00 UTC / 18:30 IST weekdays).
  Also `POST /api/sme-signals/refresh` (background, 409 if already running).

|---|---|---|---|

  exit code), so there is no separate cron entry; the module stays independently runnable via
  `--backfill` / `--recompute SYMBOL` / `--recompute-all`.

## Portfolio Aggregator

A personal net-worth tracker: `profiles` → `accounts` → `assets`, with `holdings` / `valuations` /
`transactions` hanging off an asset. Backing modules: `backend/routes/portfolio_aggregator.py` (CRUD
API under `/api/portfolio/*`), `backend/portfolio_valuation.py` (auto-valuation + XIRR),
`backend/cas_import.py` (CAMS/KFintech CAS PDF), `backend/csv_import.py` (broker CSV/XLSX).

**No auth or ownership column, by design.** `profiles` is a bare picker for a
localhost/Tailscale-only household tool — it is deliberately unconnected to `users`/`sessions`. This
is a disclosed scope call, not an oversight, and it means **these six tables hold real personal
financial data with no row-level access control**. Do not expose this deployment publicly without
first adding one.

- **Reads:** `compute_networth()` and the asset list, both via a correlated scalar subquery for the
  latest `as_of` per asset — deliberately not `LEFT JOIN LATERAL`, which SQLite (the test backend for
  these tables) cannot parse.
- **Lifecycle:** `refresh_valuations()` runs as the fourth, isolated step of
  `eod_prices_pipeline.run()` (so a fresh EOD close/NAV feeds a same-day valuation on the next

| Column | Type | Null | Default |
|---|---|---|---|
| `id` | `INTEGER` | no | identity (PK) |

| `date` | `DATE` | no | — |

  SQLAlchemy's JSON comparator (`transactions.c.meta["source"].as_string()`), portable across the
  Postgres and SQLite backends.
- **Two import paths with deliberately different idempotency models:**
  - `cas_import` — **replacement.** A CAS PDF is always the *complete* statement for a folio, so
    `_write_transactions()` deletes every existing `meta.source='cas'` row for the matched asset
    first, then inserts fresh. Manual and CSV-sourced rows for the same asset are untouched.
  - `csv_import` — **append + dedup.** A broker tradebook is a date-ranged partial, never a full
    restatement, so rows are appended; a row is treated as a duplicate only when an existing
    `meta.source='csv'` transaction for the same asset has an identical `(date, type, units, amount)`.
    Re-uploading the same file, or an overlapping date range, is safe.
- **Reads:** `portfolio_valuation.xirr_report(engine, profile_id)` — `_FLOW_SIGNS` maps
  `buy → −amount`, `sell → +amount`, `dividend → +amount`; everything else is ignored. Notably
  `dividend_reinvest` (written by `cas_import`) is intentionally absent from that map: a reinvested
  dividend is not money entering or leaving the portfolio. The asset's latest `valuations` row is
  appended as the terminal cashflow. An asset with no transactions returns `null` and is excluded
  from the pooled portfolio XIRR entirely.

## Migrations

Alembic, configured at `backend/alembic.ini` + `backend/migrations/env.py`. **All commands run from
`backend/`.** `env.py` imports `db.models.metadata` directly as `target_metadata` (no second,
Alembic-specific model layer) and reads `DATABASE_URL` from the environment — `alembic.ini`'s own
`sqlalchemy.url` is deliberately left blank so there is one place to configure a connection string.

### The 3-revision chain

| Revision id | File | `down_revision` | Adds |
|---|---|---|---|
| `0001` | `0001_baseline_schema.py` | `None` | The original 11 tables: `users`, `magic_links`, `sessions`, `api_keys`, `watchlist_items`, `positions`, `verdict_history`, `mf_holdings_history`, `sme_stocks`, `ema_signals`, `screener_stocks` |
| `684c8a31e7e0` | `684c8a31e7e0_add_eod_price_store_and_corporate_.py` | `0001` | `securities`, `prices_daily`, `mf_nav_daily`, `corporate_actions` |
| `8613aafc2d9d` | `8613aafc2d9d_add_portfolio_aggregator_foundation_.py` | `684c8a31e7e0` | `profiles`, `accounts`, `assets`, `holdings`, `valuations`, `transactions` |

The revision **id** of the baseline is `0001`, not the filename stem `0001_baseline_schema`. Alembic
resolves by the `revision` string inside the file; `alembic stamp 0001_baseline_schema` fails with
`Can't locate revision identified by '0001_baseline_schema'`.

### Fresh database

```bash
cd backend
alembic upgrade head
```

### Database predating Alembic

Such a deployment already has the original 11 tables (created by hand from `db/schema.sql`, or by a
pipeline's `--setup-db` calling `metadata.create_all()`), so replaying `0001`'s `CREATE TABLE`
statements would fail on the first one. Stamp the baseline specifically, then upgrade forward:

```bash
cd backend
alembic stamp 0001      # "the original 11 tables already exist"
alembic upgrade head    # actually creates the 10 newer tables
```

**A bare `alembic stamp head` is wrong here.** It marks all three revisions applied, including the two
that were never run, so the 10 tables of the EOD price store and Portfolio Aggregator are never
created — and nothing fails at migration time. The breakage surfaces later at runtime, as
`relation "prices_daily" does not exist` from a cron job and a 503 from every
`/api/portfolio/*` endpoint. (A bare `stamp head` *was* correct back when `0001` was the only
revision; that instruction became wrong the moment a second one landed.)

### Adding a schema change

```bash
cd backend
# edit db/models.py first
alembic revision --autogenerate -m "what changed"
alembic upgrade head
```

Do not hand-edit `db/schema.sql` to match — that hand-synced convention is superseded. A generated
revision has an explicit up *and* down path, a real ordering, and autogenerate diffs against the
actual live schema rather than trusting a remembered `ALTER TABLE ... IF NOT EXISTS` guard.

### `stamp_alembic_head()`

`db/models.py::stamp_alembic_head()` closes a drift vector between the two setup paths.
`sme_ema_pipeline.py --setup-db`, `screener_pipeline.py --setup-db`, and
`eod_prices_pipeline.py --setup-db` all call `metadata.create_all()` directly, bypassing Alembic — a
database created that way would have the tables but no `alembic_version` row, and a later
`alembic upgrade head` would fail on tables that already exist. Each `--setup-db` therefore calls
`stamp_alembic_head()` immediately afterwards. It never raises: a stamp failure (e.g. `alembic.ini`
not found from an unusual working directory) is logged and swallowed, since the tables themselves
were already created successfully.

## `--reset-db` blast radius

**Rule for anyone adding a new pipeline: scope your reset to your own tables. Never call
`metadata.drop_all(engine)`.**

All 21 tables register on one shared `MetaData()`, so `drop_all()` drops *everything* — including
`users`, `sessions`, and the six Portfolio Aggregator tables holding real personal financial data
that is not regenerable from any pipeline. Every pipeline in the repo now scopes its own reset:

| Command | Drops/recreates |
|---|---|
| `python sme_ema_pipeline.py --reset-db` | `ema_signals`, `sme_stocks` (in FK order: child dropped first, parent created first) |
| `python screener_pipeline.py --reset-db` | `screener_stocks` |
| `python eod_prices_pipeline.py --reset-db` | `securities`, `prices_daily`, `mf_nav_daily` |
| `python corporate_actions_pipeline.py --reset-db` | `corporate_actions` |

Implemented as `table.drop(engine, checkfirst=True)` / `table.create(engine, checkfirst=True)` per
table, or `metadata.create_all(engine, tables=[...])`.

`--setup-db` is a different matter: it still calls a full `metadata.create_all(engine)` in
`sme_ema_pipeline.py` and `screener_pipeline.py`, which is safe (it only creates missing tables,
never alters or drops) and is what makes `stamp_alembic_head()` correct to call afterwards.
`eod_prices_pipeline.py --setup-db` is scoped to its own three tables.

> Historical note: `sme_ema_pipeline.py --reset-db` originally *did* call `metadata.drop_all()` and
> silently wiped accounts, sessions, and watchlists along with its own two tables. Both the code and
> the docs describing it have been corrected; the rule is now stated as a binding constraint in the
> root `CLAUDE.md` and in `backend/CLAUDE.md`'s "Important Rules for Claude".

`corporate_actions_pipeline.py --setup-db` creates `corporate_actions` but does **not** call
`stamp_alembic_head()`, unlike the other three `--setup-db` commands. Harmless in the normal
order (an earlier pipeline's setup will already have stamped), but it is the same drift vector
that helper exists to prevent — a database whose *only* setup call was this one ends up with the
table and no `alembic_version` row.

## Hashed secrets

Three tables store credentials, and none of them stores a raw one. Every token is a
`secrets.token_urlsafe(32)` string, persisted only as its `hashlib.sha256(...).hexdigest()` in a
`VARCHAR(64)` column:

| Table | Column | Where the raw value exists |
|---|---|---|
| `magic_links` | `token_hash` | The outbound sign-in email, and the process memory that generated it. Never returned by any endpoint. |
| `sessions` | `token_hash` | The httpOnly `alphapulse_session` cookie on the Next.js origin, and the `Authorization: Bearer` header the proxy forwards. `GET /api/auth/verify`'s response body carries only `{user}` past the one proxy hop that sets the cookie, so page-level JS (and an XSS on that origin) can never read a live session token out of a fetch response. |
| `api_keys` | `key_hash` | The single `POST /api/api-keys` 201 response that mints it. Shown once, in a copy-to-clipboard box. `GET /api/api-keys` returns `key_prefix` only. |

Consequences worth being explicit about:

- A full database leak does not let an attacker sign in as anyone or call `/api/v1/*`.
- There is no "resend my API key" — it is unrecoverable by design. Revoke and mint a new one.
- Lookups are by hash equality against a `UNIQUE` index, so they are exact-match only; there is no
  prefix search over `token_hash`/`key_hash`.
- `api_keys.key_prefix` is explicitly **not** a secret — it exists so the UI can tell keys apart.

## `DATABASE_URL` is optional

The core product — single-stock analysis — runs with no Postgres at all. What a missing or
unreachable database degrades to differs by feature, and the difference is deliberate: a section
supplementing a report that already loaded must not look like the whole analysis failed, whereas an
endpoint whose entire purpose is the database should say so.

| Feature | Without `DATABASE_URL` |
|---|---|
| `GET /api/analyse/{symbol}` (stock analysis) | **Works fully.** Scrapers, signal engine, and analyst are all file-cache-backed. |
| `GET /api/market-picks` | **Works fully.** Cache is `output/_market_picks/picks.json`, not Postgres. |
| `verdict_history.save_snapshot()` | **Silent no-op**, logged. Never raises — a persistence failure must not break the pipeline. |
| `mf_holdings_history.save_snapshot()` | **Silent no-op**, logged. Same convention. |
| `GET /api/verdict-history/{symbol}` | **200** with `{"history": [], "win_rate": null, "scored_count": 0}` — not 503. The verdict-timeline strip just does not render. |
| `GET /api/consolidated/{symbol}` | **200.** The SME section is `null`; the analysis and market-pick sections still resolve from file cache. A DB error there is caught so it cannot fail the other two. |
| `GET /api/watchlist/calendar` | **Works.** Takes its symbol list from the caller and reads the file cache — no DB dependency at all. |
| `/api/watchlist*`, `/api/positions*` | **503** `"DATABASE_URL not configured."` via `routes/_shared.py::run_owned_db_call()`. |
| `/api/sme-signals*` | **503** `"DATABASE_URL not configured. Run the SME pipeline first."` |
| `/api/screener*` | **503** `"DATABASE_URL not configured. Run the screener pipeline first."` |
| `POST /api/auth/request-link`, `GET /api/auth/verify` | **503.** These are the only two auth endpoints that return 503. |
| `GET /api/auth/me`, `/api/api-keys*` | **401** `"Not signed in."` — the DB check is folded into the same guard as the missing-token check (`api.py:2596`, `_require_session_user`), so an unconfigured DB is indistinguishable from being signed out. |
| `POST /api/auth/logout` | **200** `{"ok": true}`. Deliberate: logout is best-effort, and with no DB there is no session row to delete. |
| `/api/portfolio/profiles\|accounts\|assets\|networth\|xirr` | **503.** |
| `/api/portfolio/concentration` | **503** (it reads `positions`). |
| `/api/v1/consolidated/{symbol}` | **401** `"Missing or invalid X-API-Key header."` — not 503. `_require_api_key_user()` checks `DATABASE_URL` in the same condition as the missing-key check (`api.py:2740`), so a caller cannot distinguish an unconfigured server from a bad key. |
| `sme_ema_pipeline.py` / `screener_pipeline.py` / `eod_prices_pipeline.py` / `watchlist_alerts.py` | **Fail loudly** and exit non-zero. Unattended cron jobs must not "succeed" with nothing written. |
| Alembic | Unusable — `migrations/env.py` reads the same env var. |

A DB error that is not a missing `DATABASE_URL` is sanitized before it reaches the client
(`"Database error. See server logs."`) — no raw exception text in any response body.

## Retention and pruning

Only three things in this schema clean up after themselves. Everything else grows monotonically.

| Table | Policy | Trigger |
|---|---|---|
| `ema_signals` | ~100 calendar days (`sme_ema_pipeline._RETENTION_DAYS`), ≈ the 63 trading days (`_STORE_DAYS`) actually stored plus buffer. | `_prune_signals()` at the end of every pipeline run. |
| `magic_links` | Expired rows deleted (`WHERE expires_at < NOW()`); TTL 15 min. | Opportunistically, at the top of every `auth.create_magic_link()` transaction. No cron. |
| `sessions` | Expired rows deleted (`WHERE expires_at < NOW()`); TTL 30 days. | Same transaction as `magic_links` above — i.e. only when *someone requests a sign-in link*. Idle deployments never prune. Harmless (expiry is enforced on read) but not self-cleaning. |

**No retention policy at all:** `prices_daily` and `mf_nav_daily` (unbounded, one row per
symbol/scheme per day forever), `verdict_history`, `mf_holdings_history`, `corporate_actions`,
`transactions`, `valuations`, revoked `api_keys`, and orphaned `watchlist_items`/`positions` whose
`client_id` browser cleared its `localStorage`.

For scale context: `prices_daily` at ~2000 symbols × ~250 trading days is ~500k rows/year, which is
unremarkable for Postgres but is the only table here with a real growth curve.

Two non-DB stores follow the same instinct and are worth knowing about when tracing data flow, even
though they are files, not tables: `signals_data/<SYMBOL>/<date>.json` (write-only audit trail,
pruned to 90 days per symbol on every write by `signals/store._prune_old_signals`) and
`output/_extract_cache/` (pruned once per market-picks run by `_prune_extract_cache()`).

## Known schema gaps

Genuine findings from reading `db/models.py` against its callers. None is currently causing a
production failure; they are recorded so the next person does not have to rediscover them.

1. **No `ON DELETE` action on any FK to `users`.** `sessions`, `api_keys`, `watchlist_items`, and
   `positions` all reference `users.id` with a bare FK. A `DELETE FROM users` would fail with a
   foreign-key violation rather than cascading. Currently harmless — no user-deletion path exists
   anywhere in the codebase — but the day account deletion is implemented (GDPR "delete my account",
   an admin tool), it needs either `ON DELETE CASCADE` on all four or an explicit multi-table delete
   in the right order. Same for `ema_signals.symbol → sme_stocks.symbol` and the Portfolio
   Aggregator's `profiles → accounts → assets → {holdings, valuations, transactions}` chain: deleting
   a profile today requires deleting four levels of children by hand.

2. **`screener_stocks` is indexed on the two columns nobody filters by numerically, and on none of
   the four that are.** Indexes exist on `nse_industry` and `sector`; `GET /api/screener` filters on
   `pe_ratio`, `market_cap_cr`, `rsi14`, and `ema_trend`, and sorts on `current_price`, `pe_ratio`,
   `market_cap_cr`, `avg_volume_10d`, `rsi14`. At ~500 rows a sequential scan plus sort is genuinely
   the right plan and adding indexes would be premature — but the mismatch is worth knowing before
   anyone widens the universe past NIFTY 500.

3. **`assets.symbol` has no index**, and both `csv_import`'s "does a stock asset already exist for
   this symbol" lookup and `eod_prices_pipeline._held_scheme_codes()`'s
   `WHERE type='mf' AND archived=FALSE` scan it. Fine at household scale (tens of rows); it becomes
   an N-scans-per-import problem only if this ever grows.

4. **`accounts.type` and `assets.type` are validated only in application code.** Every other
   enum-like column in this schema either has a `CHECK` (`users.tier`) or is genuinely open
   (`corporate_actions.type` has a documented `other` bucket). A direct `INSERT` — or a future second
   writer — can put an unrecognized value in these two, and `compute_networth()`'s loan-subtraction
   branch would silently misclassify it.

5. **`prices_daily.close` is nullable, and `adj_close` is read by nobody.**
   `portfolio_valuation._latest_close()` correctly guards with `AND close IS NOT NULL`, so no caller
   assumes non-null today. But note that it reads raw `close`, not `adj_close` — the whole
   corporate-actions adjustment pipeline currently has zero readers. That is consistent with the
   store's documented "ingestion-only" scope, but it means the adjustment logic is unexercised by any
   product surface and would be the first thing to verify before something starts depending on it.

6. **`transactions` has no unique constraint**, so both importers' idempotency is enforced entirely
   in Python. `cas_import`'s delete-then-insert is safe under any interleaving of one importer, but
   `csv_import`'s "is there an identical `(date, type, units, amount)` row" check is a read followed
   by a write with no lock — two concurrent uploads of the same overlapping tradebook could both pass
   the check and both insert. Unlikely for a single-user tool driven by a file picker; a real fix is
   a partial unique index, not more application code.

7. **`sessions` pruning is coupled to sign-in-link traffic.** Both the `magic_links` and `sessions`
   deletes live in `create_magic_link()`'s transaction. A deployment where every user stays signed in
   accumulates expired session rows indefinitely. Expiry is checked on read, so this is storage
   growth, not an auth hole.

8. **`securities.isin` is neither unique nor indexed**, yet `tools/securities_master` dedupes the
   merged registry by ISIN. The dedupe happens in Python over a full in-memory load, so this is not a
   correctness bug — but nothing at the schema level prevents two symbols sharing an ISIN, which
   would make that dedupe's "NSE main-board wins" tiebreak the only thing deciding which one is
   reachable.
